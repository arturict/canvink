# Canvink Collab Sync — Protocol & Architecture (v1)

Single source of truth for the notebook-sharing feature. The backend worker,
the frontend client module, and the UI integration are all built against this
document. Change it only together with all three parts.

## Product behavior

1. The owner shares a notebook from the app. The room starts **restricted**: nobody
   gets in until the owner (or an admin) invites a person by e-mail address with a
   role, or switches the read-only link on.
2. Roles are per person: **Lesen** (`viewer`, read only), **Bearbeiten** (`editor`),
   **Admin** (`admin`: edits and manages sharing) and the implicit **owner**, who cannot
   be removed or demoted by anyone. See "Sharing roles" below.
3. Everybody who only has the link is a **reader**, always. The server decides that;
   a client cannot ask for more. The link can be switched on and off and regenerated.
4. In the app the invitee signs in / signs up (Clerk). An invitation names an e-mail
   address; the account that owns that address as a *verified* Clerk address (primary
   or secondary) is let in with the invited role. Nothing is e-mailed: the invitation
   shows up under "Mit dir geteilt" in the notebook switcher.
5. The owner edits from their own device without Clerk (local-first app; the
   room's `ownerToken` proves ownership). Clerk is optional for the owner; a signed-in
   owner also announces their account (`PUT /owner-profile`) so the member list shows
   them and so they can open the notebook from another signed-in device.

## Topology

- Backend: Cloudflare Worker + one **SQLite-backed Durable Object per room**
  (`NotebookRoom`). A room corresponds to one shared notebook, or (see
  "Personal space (v2)" below) to one signed-in user's own workspace.
- The server never runs Automerge. It stores and relays **opaque change
  payloads** and snapshots. Clients (which run Automerge WASM) merge.
- Transport: WebSocket for live sync, HTTPS for room management.

## Identifiers and secrets

- `roomId`: 22-char base64url random, generated by the server at room creation.
- `ownerToken`: 32-byte base64url random, returned once at creation. Stored
  client-side by the owner. Proves owner role.
- Share link: `<app-origin>/app#join=<roomId>.<linkSecret>` where
  `linkSecret` is a 32-byte base64url random generated at share-link creation.
  The secret lives in the URL fragment so it is never sent to the app host or
  recorded in HTTP logs. The server stores only `sha256(linkSecret)`.
- Anonymous viewers identify with a client-generated `guestId` (UUID) — purely
  informational (presence/labels), never an authorization input.

## Roles

| Credential presented                  | Role    |
|--------------------------------------|---------|
| `ownerToken`, or the account that registered with `PUT /owner-profile` | owner (everything; cannot be demoted or removed) |
| valid Clerk JWT of a member with role `admin` | admin (edit, plus invite, change roles, remove people, manage the link) |
| valid Clerk JWT of a member with role `editor` | editor (read/write) |
| valid Clerk JWT of a member with role `viewer`, or any account that joined through the link | viewer (read only) |
| valid Clerk JWT whose **verified** e-mail address has a pending invitation | the invited role (the invitation is claimed on first use) |
| `linkSecret` only (no account), link on | viewer (read only) |
| anything else                         | rejected |

Role enforcement is entirely server-side, on every operation:

- Reads (hello catch-up, `fetch`, room asset GET/HEAD, presence) are open to every role.
- Writes need `owner`, `admin` or `editor`: `append`, `snapshot`, `announce`, `remove` frames
  answer `error: "read-only"` and touch nothing; `PUT /rooms/:id/assets/:hash` answers
  `403 read-only`. A viewer's presence `state.ink` is dropped (their pointer and page are
  relayed, their live strokes are not).
- Managing sharing (`/members`, `/invites`, `/link*`, the legacy `/links`) needs `owner` or
  `admin`; everybody else gets `403 forbidden`. `DELETE /rooms/:id`, `DELETE /collaborators`
  and `PUT /owner-profile` stay owner-token only.
- **A link only ever makes a reader.** `hello.auth = {"kind":"user","jwt","linkSecret"}` and
  `{"kind":"link"}` resolve to `viewer` whatever else the client sends; a member who already
  holds a higher role keeps it (the link never lowers or raises anyone). A link secret in
  `X-Link-Secret` reads (`/meta`, room assets) and nothing else.
- The role is re-read from storage on every frame after `hello`, not trusted from the
  socket's attachment. A changed role is pushed (`{"t":"role","role":"viewer"}`) and applies
  to the very next frame; a removed member's next frame closes the socket (`4401`).

This table describes a **`kind: "shared"`** room only. See "Personal space (v2)" below for
`kind: "personal"`, which uses a different, single-credential role model.

### Members, invitations and the link

State per room (SQLite): `collaborators` (`sub`, `role`, `via`, `name`, `email`, `emails`,
`picture`, `addedAt`), `invites` (`email`, `role`, `invitedBySub`, `invitedByName`,
`createdAt`) and the meta keys `linkEnabled`, `linkSecret`, `ownerSub`, `ownerName`,
`ownerEmail(s)`, `ownerPicture`, `roomId`.

`via` says how a member got in: `invite` (named by an admin or by an e-mail invitation),
`link` (joined through the link; revoked when the link is turned off or regenerated) or
`migrated` (a collaborator from before roles existed: they became `editor` and are not
affected by the link). A role change by name turns a `link` member into a named member.

- **Link on/off.** New rooms start with the link off; a legacy room counts as on while it
  has link rows. Turning the link off, or regenerating it, deletes the `via = "link"`
  members, closes their sockets and every anonymous link socket (`4401`). Named members are
  never touched. The current secret is stored in meta (admins copy it) next to the hashes
  that authenticate links.
- **Invitations.** `POST /invites` stores `{email, role}` (lower-cased, one per address, at most
  100 per room) and writes an index entry to the **inbox** Durable Object of that address.
  An account claims it when it connects (`hello` with `kind: "user"`, or an HTTP bearer) and
  one of its verified addresses has an invitation: it becomes a member with the invited role
  (never lowering a higher one) and the invitation and inbox entry are deleted.
- **Verified addresses** come from the Clerk Backend API (`GET /v1/users/:sub`, the
  addresses whose `verification.status` is `verified`, secondary ones included; needs the
  secret `CLERK_SECRET_KEY`) and from the session token if the Clerk instance adds an
  `emails` claim (or `email` with `email_verified: true`). Without either nobody can claim
  an invitation (fail closed). Results are cached per isolate for 60 s.
- **Inbox.** One `NotebookRoom` Durable Object per address (`idFromName("inbox-v1:" +
  sha256hex(email))`, `meta.kind = "inbox"`, no wrangler migration needed) lists the rooms
  that invited it. It is an index only: listing grants nothing, claiming happens in the room.

## Clerk verification (backend)

- Env vars: `CLERK_ISSUER` (e.g. `https://<slug>.clerk.accounts.dev`),
  `CLERK_JWKS_URL` (defaults to `${CLERK_ISSUER}/.well-known/jwks.json`),
  `CLERK_AUTHORIZED_PARTIES` (optional, comma-separated).
- Verify RS256 JWT via WebCrypto against cached JWKS (cache 1 h, refetch on
  unknown `kid` once). Check `iss`, `exp`, `nbf`. The `sub` claim is the
  collaborator identity.
- **`CLERK_ISSUER` is mandatory for real-JWT verification (fail-closed,
  D5)**: if it is unset, every real Clerk JWT is rejected outright — there is
  no "skip issuer check" fallback. An *empty string* is not treated as
  "unset" anywhere in config; it must simply not be declared. The test shim
  below is unaffected by this.
- If `CLERK_AUTHORIZED_PARTIES` is set, the JWT's `azp` claim must be one of
  the comma-separated values, or verification fails.
- **Test shim**: if env `TEST_AUTH_SECRET` is set (never in production
  config), a token of the form `test:<sub>:<hmacSha256(sub, TEST_AUTH_SECRET)
  as base64url>` is accepted with identity `<sub>`. Unit/e2e tests and local
  dev use this; the production wrangler env omits `TEST_AUTH_SECRET`.

## HTTP API (JSON; CORS enabled for the app origin, configurable via env `ALLOWED_ORIGINS`)

All under `/api/v1`. CORS is a **response shield only**: it decides which
browser origins may read a response, not whether a request is authorized —
every route below still checks its own credential regardless of `Origin`.

- `POST /rooms` — body `{ notebookTitle: string }`. No auth required
  (local-first owner). Response `201 { roomId, ownerToken }`.
  - Rate-limited per `CF-Connecting-IP` (B3), target 10 room creations / 60s.
    **What's actually shipped by default is a best-effort, per-isolate
    in-memory limiter** (`src/rateLimit.ts`) — not a durable, globally
    accurate limit. It resets on cold start and doesn't share state across
    isolates, so a determined abuser spread across enough isolates (or
    across cold starts) sees a materially higher effective ceiling than
    "10/60s" implies. The real Cloudflare Rate Limiting binding, which would
    enforce this accurately, is deliberately commented out in
    `wrangler.jsonc` (see its comment and the README's rate-limiting
    section for why) — enabling it is the correct upgrade path before this
    matters at real abuse volume. Either way, requests over the effective
    limit get `429`.
  - `notebookTitle` must be a string ≤200 chars, or a non-string/oversized
    value → `400`. A non-JSON body or a JSON body that isn't an object (e.g.
    a bare array) → `400` (never an unhandled exception).
- `POST /rooms/:roomId/links` — owner or admin (`Authorization: Owner <ownerToken>` or
  `Bearer <jwt>` of an admin). Switches the link on and mints one more secret.
  Response `201 { linkSecret }`. Capped at 20 live links per room → `400` past the cap.
  Kept for old clients; the app uses `PUT /link`.
- `DELETE /rooms/:roomId/links` — owner or admin; turns the link off, deletes its secrets and
  revokes the people who came in through it (see "Members, invitations and the link").
  Named members are unaffected.
- `DELETE /rooms/:roomId/collaborators` — owner only; removes every member and every pending
  invitation and closes the sockets of all accounts. Kept for old clients; the share dialog
  removes people one by one with `DELETE /members/:sub`.
- `DELETE /rooms/:roomId` — owner only; full unshare. Wipes every table for
  the room (`storage.deleteAll`) and immediately closes **every** live
  WebSocket in the room (owner included) with code `4401`. The room then
  reads back as not-found/unauthorized on every route. This is the recovery
  path if `ownerToken` is ever suspected compromised (e.g. via XSS reading
  the app's `localStorage`) — there is no separate token-rotation endpoint.
- `GET /rooms/:roomId/meta` — auth via any valid credential
  (`Authorization: Owner ...`, `Authorization: Bearer <clerk-jwt>` for
  registered collaborators, or header `X-Link-Secret: <linkSecret>`);
  response `{ notebookTitle, role, docCount }`. Used by the join screen.
  - **D2**: the link secret travels as the `X-Link-Secret` header, never a
    query string. A query param (`?k=...`) is not accepted at all — request
    URLs (including query strings) show up in Workers observability logs,
    headers do not. Both the worker and `src/collab/http.ts` were updated
    together; there is no deployed version that ever accepted `?k=`, so no
    transition period was needed.

### Sharing management (owner and admins)

All of these need `owner` or `admin` (`Authorization: Owner …` or `Bearer <jwt>`); anything
else answers `401` (no valid credential, or an unknown room) or `403 {"error":"forbidden"}`.

- `GET /rooms/:id/members` → `{ notebookTitle, you:{role,sub?}, owner:{name?,email?,picture?},
  members:[{sub,role,via,addedAt,name?,email?,picture?}], invites:[{email,role,createdAt,
  invitedByName?}], link:{enabled,linkSecret|null} }`.
- `POST /rooms/:id/invites` `{email, role}` (`role` ∈ `viewer|editor|admin`) → `201`. Errors:
  `invalid-email`, `invalid-role`, `is-owner` (409), `already-member` (409),
  `too-many-invites`. Inviting an address again changes the invited role.
- `DELETE /rooms/:id/invites/:email` → `204`.
- `PATCH /rooms/:id/members/:sub` `{role}` → the member. `404 not-a-member`,
  `403 owner-protected` for the owner. Open sockets receive `{"t":"role"}` at once.
- `DELETE /rooms/:id/members/:sub` → `204`; `403 owner-protected` for the owner. Open sockets
  of that account are closed with `4401`.
- `PUT /rooms/:id/link` `{enabled}` → `{enabled, linkSecret}`. On reuses the stored secret
  (or mints one for a legacy room); off revokes link members and closes link sockets.
- `POST /rooms/:id/link/regenerate` → `201 {enabled:true, linkSecret}`; the old link and the
  access that came through it end.
- `PUT /rooms/:id/owner-profile` `{jwt}` — owner token only. Stores the owner's account
  (`ownerSub`, name, verified addresses, picture): shown in the member list, protected from
  invitation (`is-owner`), and the account counts as owner on other devices.
- `POST /rooms/:id/leave` — `Bearer <jwt>` of a member; removes them (the owner cannot leave).

### Invitations of the signed-in account

- `GET /api/v1/me/invitations` (`Bearer`) → `{ invitations:[{roomId, notebookTitle, role,
  invitedBy?, createdAt}] }` for the account's verified addresses (highest role per room).
- `DELETE /api/v1/me/invitations/:roomId` (`Bearer`) → `204`; withdraws the invitations
  that address the account's verified addresses in that room.

Each room additionally bounds docs (≤1000 per room, checked on the first
`announce`/`snapshot` for a new `docId`) and registered collaborators (≤100;
past the cap, new collaborator registration attempts are silently ignored
rather than erroring — the JWT's owner still gets a normal `viewer`/`editor`
response for that connection based on whatever role they already hold).

## WebSocket protocol

Connect: `GET /api/v1/rooms/:roomId/ws` upgraded. First client frame must be
`hello`. Frames are JSON text frames; binary payloads are base64url fields
(v1 keeps it simple; payload sizes are bounded below).

### Client → server

- `{"t":"hello","auth":{...},"since":{"<docId>":seq,...}}`
  where `auth` is one of
  `{"kind":"owner","ownerToken":"..."}` /
  `{"kind":"link","linkSecret":"..."}` /
  `{"kind":"user","jwt":"...","linkSecret":"..."}` (linkSecret optional if
  already a collaborator).
  `since` carries the highest seq per doc the client already has (resume).
- `{"t":"append","docId":"...","payload":"<base64url automerge incremental change bytes>"}`
  — editors/owner only.
- `{"t":"snapshot","docId":"...","payload":"<base64url full automerge save>","covers":seq}`
  — editors/owner only. Compaction: replaces the log for `docId` up to
  `covers`; server keeps changes with seq > covers.
- `{"t":"announce","docId":"...","kind":"notebook"|"page"}` — editors/owner
  declare a doc belongs to the room (new page created). First `snapshot` or
  `append` for an announced doc initializes it.
- `{"t":"remove","docId":"..."}` — editors/owner; deletes a doc's data
  (page permanently deleted).
- `{"t":"ping"}` → server answers `{"t":"pong"}`.
- `hello.lazy: true` (personal rooms only) — the catch-up leaves out every
  `page` doc for which `hello.since` has no entry. The client asks for those
  itself with `fetch`, so a fresh device receives the workspace and notebook
  docs (kilobytes) instead of the whole account before it can show anything.
  The `welcome` carries `"lazy": true` when the room honoured the flag; a
  client must treat a `welcome` without it as a full replay (an older Worker
  ignores the flag).
- `{"t":"fetch","id":"...","docIds":["..."],"since":{"<docId>":seq}}` — any
  role that completed `hello`. At most 64 `docIds`. The room replays each
  existing doc exactly like the `hello` catch-up (snapshot unless `since`
  already reaches `covers`, then the changes after it) and ends with
  `{"t":"fetched","id":"...","docIds":[...],"known":[...]}` where `known`
  lists the requested docs the room has. Frames are handled one at a time, so
  anything broadcast after the reply is newer than the reply. `id` is echoed
  so several fetches can be in flight.

Every client frame is strictly validated per-type before dispatch (D6):
unexpected/missing/mistyped fields (including non-base64url `payload`
strings) never reach a handler. A first frame that isn't `hello`, or is
`hello` but structurally invalid, closes the socket with code `4400` after
a `bad-frame` error frame. Any other frame that fails validation gets a
non-fatal `bad-frame` error and is dropped — the socket stays open and
usable. An unexpected exception anywhere in frame handling (should not
happen given the validation above, but is not assumed impossible) sends a
`bad-frame` error and closes with code `1011`, rather than leaving the
socket wedged with no response.

### Server → client

- `{"t":"welcome","role":"owner"|"admin"|"editor"|"viewer","docs":[{"docId","kind"}],"notebookTitle":"..."}`
  then, for each doc, the catch-up sequence:
  - `{"t":"snapshot","docId","payload","covers":seq}` — sent **only** when a
    snapshot exists for the doc *and either* the client's `hello.since` has no
    entry for this `docId` at all (a brand-new join — it has never seen this
    doc, so it needs the snapshot no matter what `covers` happens to be, even
    `0`) *or* it has an entry that is still behind `covers`
    (`since[docId] < covers`). A client with an explicit `since[docId]` that
    already reaches or exceeds `covers` already holds everything the
    snapshot would give it; skipping it there is both an efficiency win and,
    together with the client-side merge behavior below, part of the B1
    reconnect-data-loss fix (previously the snapshot was *always* resent and
    the client *replaced* its doc with it, silently discarding every local
    change made since the initial share). The distinction between "no entry"
    and "entry present and equal to `covers`" matters: `covers` defaults to
    `0` for any doc that has never been compacted, which is indistinguishable
    from "the client already has `0` worth of state" unless the client's
    `since` map is checked for key presence, not just value.
  - `{"t":"append","docId","payload","seq":n}` for each retained change with
    seq greater than `max(covers, client since[docId])`.
  - Ends with `{"t":"synced"}`. A lazy hello (see above) skips the pages it
    did not resume; the `welcome` still lists them, so a client knows which
    docs exist before it holds any of them.
- Live: every accepted `append`/`snapshot`/`announce`/`remove` is broadcast to
  all other connected sessions with the same frame shape (`append` gains
  `"seq"`).
- `{"t":"seq","docId":"...","seq":n}` — sent **only to the socket that sent
  the `append`** (never broadcast), acknowledging it was accepted and
  assigned `seq`. Drives client-side compaction (see below).
- `{"t":"role","role":"owner"|"admin"|"editor"|"viewer"}` — the room changed this socket's role
  while it was open (a promotion or a demotion). Clients that predate it ignore it as an
  unknown frame; the room enforces the role regardless.
- `{"t":"error","code":"read-only"|"unauthorized"|"payload-too-large"|"unknown-doc"|"bad-frame","detail":"..."}`
  Fatal errors (`unauthorized`) close the socket with code 4401; `read-only`
  and `bad-frame` are non-fatal (frame dropped, socket stays).

### Presence (ephemeral)

Presence tells the others in a room who is there, on which page, where their
pointer is, what they are drawing right now and which region they work in.
It is relayed, never stored, and never part of the change log.

- Client → server: `{"t":"presence","state":{...}}`. Any authenticated role
  may send it, viewers included. `state` must be a JSON object of at most
  16 KiB serialized (`payload-too-large` otherwise, non-fatal); the server
  does not interpret it. Each socket has a token bucket (60 frames burst,
  40 per second refill); frames past it are dropped silently.
- Server → other sockets: `{"t":"presence","from":"<connId>","role":"owner"|"admin"|"editor"|"viewer","state":{...}}`.
  `connId` is a random id the server assigns per socket at `hello`; it is
  never the Clerk `sub`. `role` is stamped by the server, so a client can
  ignore live ink from a viewer socket.
- Server → other sockets: `{"t":"presence-leave","from":"<connId>"}` when a
  socket that had sent presence closes or is evicted.
- After `synced`, the server sends a joining socket the latest `presence`
  frame of every other live socket. The server keeps these in memory only;
  after the Durable Object hibernates the replay is empty until the clients'
  own heartbeat (every few seconds) refills it.
- Live broadcasts, presence included, go only to sockets that completed
  `hello`. A socket that is connected but unauthenticated receives nothing.
- Presence is not end-to-end encrypted, exactly like the document changes
  of a shared room (see the security notes below). The client-side state
  schema (`v: 1`) lives in `src/collab/presence.ts`.
- A server without presence support answers the first `presence` frame with
  a non-fatal `bad-frame` "unknown frame type"; clients then stop sending
  presence for that session.

### Limits and compaction

- Max frame size 16 MiB (payloads over 1 MB are chunked in storage); max payload per doc log 50 MB (server rejects with
  `payload-too-large`).
- Per room: ≤1000 docs, ≤20 live links, ≤100 registered collaborators (B3).
- Server stores per doc: latest snapshot (payload, covers) + ordered change
  rows `(seq, payload)` in the DO's SQLite.
- **Compaction (B1c)**: the client — not the server — decides when to
  compact, using the `seq` ack stream. After every 64 acked appends for a
  given `docId` since that doc's last compaction, the owner/editor that sent
  those appends sends a `snapshot` with `covers` set to the just-acked `seq`
  and `payload` set to its current full Automerge save for that doc. This is
  sound because the Durable Object processes frames serially and delivers
  broadcasts in order: by the time the ack for seq N arrives at the sender,
  every change with seq < N that *that sender* produced has already been
  merged into its own local doc state (it's the only writer of that state at
  that instant), so the full save at ack time genuinely covers everything up
  to N. The server never initiates compaction on its own.

## Durable Object storage schema (SQLite)

```sql
CREATE TABLE IF NOT EXISTS meta   (key TEXT PRIMARY KEY, value TEXT);
-- keys: kind ("shared"|"personal"; absent = legacy, treated as "shared"),
--       notebookTitle, ownerTokenHash, createdAt,
--       personalSub, logBytes, assetCount, assetBytes (personal rooms only —
--       see "Personal space (v2)" below)
CREATE TABLE IF NOT EXISTS links  (secretHash TEXT PRIMARY KEY, createdAt TEXT);
CREATE TABLE IF NOT EXISTS collaborators (sub TEXT PRIMARY KEY, addedAt TEXT,
  role TEXT, via TEXT, name TEXT, email TEXT, emails TEXT, picture TEXT);
CREATE TABLE IF NOT EXISTS invites (email TEXT PRIMARY KEY, role TEXT NOT NULL,
  invitedBySub TEXT, invitedByName TEXT, createdAt TEXT NOT NULL);
CREATE TABLE IF NOT EXISTS inbox (roomId TEXT PRIMARY KEY, notebookTitle TEXT NOT NULL,
  role TEXT NOT NULL, invitedBy TEXT, createdAt TEXT NOT NULL); -- inbox Durable Objects only
CREATE TABLE IF NOT EXISTS docs   (docId TEXT PRIMARY KEY, kind TEXT, snapshot BLOB, covers INTEGER DEFAULT 0);
CREATE TABLE IF NOT EXISTS changes(docId TEXT, seq INTEGER, payload BLOB, PRIMARY KEY (docId, seq));
```

**Migration.** The `collaborators` columns are added with `ALTER TABLE` on every wake when
missing, and rows without a role become `role = 'editor'`, `via = 'migrated'`: every member
from before roles existed keeps Bearbeiten, and the link no longer governs them.

`seq` is per-doc monotonic (max existing + 1). Owner/link secrets are stored
as `sha256` hex only.

`docs.kind` also accepts `"workspace"`, legal only in a `kind: "personal"`
room and only for `docId = "workspace:root"` — see below.

## Frontend module contract (`src/collab/`)

- `createRoomForNotebook(runtime, notebookId, config)` — uploads the notebook
  doc + its page docs (full automerge saves as initial snapshots), returns
  `{ roomId, ownerToken }`. The room starts restricted: no link is minted.
- `openRoomSession(config, credentials, callbacks)` — connects, exposes
  `{ role, docs, applyRemote... }`; maintains an **in-memory automerge doc
  set** for the room, applies catch-up + live frames, and for editors sends
  local changes (`Automerge.saveIncremental`-style diff bytes produced via
  `Automerge.getChanges(before, after)` equivalents from `@automerge/automerge` 3.x).
  - Incoming `snapshot` frames are **merged** (`Automerge.merge`) into
    whatever doc the session already holds for that `docId`, not used to
    replace it (B1b) — idempotent defense in depth alongside the server-side
    catch-up skip rule above, so a redundant or unexpected snapshot can
    never discard local history.
  - `RoomSession.subscribeAcked(listener)` fires once per `seq` ack frame;
    `attachAckCompaction(session, getFullSnapshotBytes, options?)` is the
    reusable helper that turns that stream into the 64-appends compaction
    behavior described above. Every room binding (`bindEditorSession` in
    `ownerBridge.ts`, used for the owner and for joined members alike) attaches it.
  - `outQueue` (frames buffered while disconnected) is capped at 1000
    entries; past the cap the oldest queued frame is dropped and `onError`
    fires with a non-fatal notice (D14) — an offline client can't grow this
    without bound.
  - Applying a `snapshot`/`append` frame is wrapped so a malformed payload
    (bad base64url, corrupt Automerge bytes) reports a non-fatal `onError`
    and is skipped rather than throwing out of the WebSocket's `onmessage`
    handler and crashing every session that receives it (D8).
- Reconnect with exponential backoff, resuming via `since`.
- The shared-session UI renders through the existing read-only page
  components; editors get the standard editor bound to the session's docs.
- Nothing from a shared session is written into the local workspace
  activation. Shared sessions live in their own surface.
- **Sharing management**: `ShareNotebookDialog` drives the routes under "Sharing
  management" (invite by e-mail with a role, role menu per person, pending
  invitations, "Allgemeiner Zugriff": only invited people or everyone with the
  link as a reader, "Link neu erstellen"). `unshareNotebook(notebookId)` deletes
  the room outright, evicting every live socket ("Freigabe beenden", owner only).
- **Read-only notebooks**: the role of the open session (`welcome`, `role` frame)
  is kept per notebook (`src/components/collab/notebookAccess.ts`). A reader's
  notebook gets the "Nur lesen" badge and no editing UI, and the documents of the
  notebook are registered as read-only (`src/storage/readOnlyDocuments.ts`): the
  storage runtime, the page writers (`applyPageElementChanges`) and the room
  session refuse local edits. A joined record without a known role is read-only
  until the room confirms the role.

  hidden), `VITE_CLERK_PUBLISHABLE_KEY` (absent ⇒ sign-in UI hidden, editing
  via link unavailable, viewing still works).
- Worker env vars: `ALLOWED_ORIGINS`, `CLERK_ISSUER?`, `CLERK_JWKS_URL?`,
  `CLERK_SECRET_KEY?` (secret; Clerk Backend API key that lists a user's verified addresses,
  required to claim e-mail invitations), `TEST_AUTH_SECRET?` (dev/test only; also accepts the
  `testv2:` token that carries verified addresses), `PERSONAL_SPACE_SALT?` (secret,
  personal space only — see below), `ASSETS?` (R2 binding, personal space
  only, not yet enabled — see below).

## Security notes (v1, explicit)

- Content is TLS-protected in transit and stored plaintext in the DO — this
  path deliberately trades E2EE for anonymous-viewer links. The existing
  `src/sync/` E2EE design remains separate and untouched.
- Editors and admins are mutually trusted within a room (no per-change server-side
  validation of automerge bytes beyond size limits). A reader cannot write, but can read
  everything the room holds, and a removed person keeps whatever they already copied.
- Link secrets travel only in the URL fragment and WebSocket frames over TLS;
  revocation via `DELETE /links`.

## Personal space (v2)

Full design: [`PERSONAL-SYNC.md`](./PERSONAL-SYNC.md). This section is a short
cross-reference from the sharing protocol above; PERSONAL-SYNC.md is
authoritative for every detail. Nothing in this section changes any route or
frame described above — the personal surface is additive, and reuses the same
`NotebookRoom` Durable Object class under a second **room kind**.

- **Room kind**: `meta.kind` is `"shared"` (or absent, for a legacy room) or
  `"personal"`. `roomExists()` is true when either an `ownerTokenHash` or a
  `personalSub` is set. Every shared-only HTTP route (`POST|DELETE /links`,
  `DELETE /collaborators`, `DELETE /` unshare) refuses a personal room with
  `403 {"error":"not-a-shared-room"}`; every personal-only route and
  `hello.auth.kind = "personal"` refuses a shared room the same way (`403`, or
  `unauthorized` + close `4401` over the socket).
- **Personal auth**: `hello.auth = {"kind":"personal","jwt":"<clerk token>"}`.
  Resolves to `role: "owner"` iff the JWT's `sub` equals the room's
  `personalSub` — no `ownerToken`, no `linkSecret`, ever, in a personal room.
  The resolved identity's JWT `exp` becomes `SocketAttachment.authExpiresAt`;
  a write (`append`/`snapshot`/`announce`/`remove`) past
  `authExpiresAt + 120s` closes the socket `unauthorized` / `4401`.
- **Reauth**: `{"t":"reauth","jwt":"<fresh clerk token>"}` →
  `{"t":"reauthed","expiresAt":n}` refreshes a live personal socket's
  deadline in place, without reconnecting. The resolved `sub` must equal the
  socket's existing `sub`; a mismatch is fatal (`4401`) — a socket never
  changes identity, same rule as a second `hello`. Non-fatal `bad-frame` on a
  non-personal socket.
- **The `workspace` doc kind**: `docs.kind` also accepts `"workspace"`, legal
  only in a personal room and only for `docId = "workspace:root"` (exactly
  one per personal room). An `announce`/`snapshot` shaped like a workspace
  doc (by `kind` or by that exact `docId`) in a shared room is a non-fatal
  `bad-frame` — a buggy or hostile client cannot smuggle a personal-shaped doc
  into a shared notebook. A personal room's `welcome.notebookTitle` is `""`.
- **Space routes** (`Authorization: Bearer <clerk jwt>`, no other credential):
  - `POST|GET /api/v1/me/space` — idempotent create-or-read. `spaceId` is
    derived server-side only, `base64url(HMAC-SHA256(PERSONAL_SPACE_SALT,
    "canvink-space-v1:" + sub)).slice(0, 22)`; a client never supplies it for
    authorization. `503 {"error":"personal-space-not-configured"}` when
    `PERSONAL_SPACE_SALT` is unset.
  - `HEAD|PUT|GET|DELETE /api/v1/me/assets/:assetId` — proxied through the
    room's Durable Object to R2, keyed `spaces/<spaceId>/<sha256hex>`. `PUT`
    streams the request body straight into R2 with the `sha256` put option
    (never buffered in the Worker); `400 checksum-mismatch` on a hash
    mismatch, `413 asset-too-large` over 64 MiB, `413 quota-exceeded` over the
    per-space asset budget, `411 length-required` without `content-length`.
    **R2 is not yet enabled on the deploy account** (`wrangler r2 bucket
    create` fails with error 10042), so the `ASSETS` binding is currently
    absent in `wrangler.jsonc` (commented out) and every asset route answers
    `503 {"error":"assets-not-configured"}` — the rest of the personal space
    (rooms, doc sync, `/me/space`) works without it.
- **Personal-room limits** (PERSONAL-SYNC.md §7): ≤5000 docs per personal
  room (vs. ≤1000 for a shared room); ≤1 GiB total change-log bytes per space,
  tracked via the `meta.logBytes` counter (`quota-exceeded`, non-fatal, when
  exceeded); ≤64 MiB per asset; ≤2 GiB total asset bytes per space, tracked
  via `meta.assetCount`/`meta.assetBytes`.
- This is a Worker-only (Wave 1) description. The client transport, the
  workspace-doc CRDT projection, the asset sync queue, and the UI are out of
  this package's scope — see PERSONAL-SYNC.md §5 onward.
